# Wac / Logio 運用マニュアル

## 1. このマニュアルの目的

このマニュアルは、2か月後に修正をしたいときに迷わないようにするための作業手順です。

基本方針は次の通りです。

- まず、ローカルで現実の画面を確認する
- 期待どおりに動いているかを人間が判断する
- 問題がないときだけ確定とする
- 確定後に、Claude Code 側で GitHub へ push する

> 重要: ビルド成功だけでは十分ではありません。見た目、数字、業務ロジックの正しさは、人間が確認する必要があります。

---

## 2. 変更の流れの全体像

変更の流れは次の4段階です。

1. 修正前に何が起きているかを整理する
2. ローカルで修正する
3. 自分の画面で動作確認する
4. 問題なければ確定して、GitHub に送る

この順番を守ることで、ミスの再発を防げます。

---

## 3. 事前に確認すること

修正前に、次を必ず確認します。

- どの画面のどこを直すのか
- どんな入力が悪いのか
- どんな期待値が正しいのか
- どのユーザー操作で再現するのか

例:

- 「現場名が重複したら、追加できない」
- 「一覧に同名現場が2件出ない」
- 「PDFの金額が変わらない」

1行で期待値をメモしておくと、あとで確認しやすくなります。

---

## 4. ローカル確認の手順

### 4-1. 開発サーバーを起動する

ターミナルで次を実行します。

```bash
npm run dev
```

成功例:

```bash
VITE v5.4.21 ready in 125 ms
Local: http://localhost:5173/
```

### 4-2. ブラウザで確認する

出てきた URL を開きます。

```text
http://localhost:5173/
```

ブラウザで実際に操作し、意図どおりに動いているかを確認します。

確認ポイント:

- 画面が想定どおりか
- ボタンが反応するか
- 入力した値が保存されるか
- 数字が合っているか
- 重複が出ていないか
- PDF 画面や出力画面も必要なら開く

> ここは省略しないこと。ビルドが成功しても、見た目や業務ロジックの誤りは見落とす可能性があります。

---

## 5. 確定の判断基準

確認後、次のどちらかで判断します。

### OK の場合

- 画面が意図どおり
- 数字が合っている
- 重複や誤動作がない
- 実務上の要件を満たしている

この場合、次の指示を出します。

> 「確定です。GitHub に送ってください。」

### NG の場合

- 見た目が崩れている
- 想定と違う動作をしている
- 数字がズレている
- エラーが残っている

この場合は、修正して再確認します。

---

## 6. 確定後の GitHub 送信手順

確定後は、Claude Code 側で以下の流れで対応します。

### 6-1. 差分を確認する

```bash
git status --short
git --no-pager diff -- src/App.jsx
```

### 6-2. 変更をコミットする

```bash
git add src/App.jsx
git commit -m "現場名重複防止と一覧重複除去を修正"
```

コミットメッセージは日本語にして、何を直したかが分かるようにします。

例:

- 「現場名重複防止と一覧重複除去を修正」
- 「同名現場の追加防止と一覧表示の重複解消」
- 「現場追加時の重複チェックと画面表示修正」

### 6-3. GitHub に push する

```bash
git push origin main
```

## 7. よくある問題と対処

### 7-1. 現場名が重複して登録される

原因:

- 追加時に重複チェックがない
- 一覧表示時に重複を除外していない
- 古いデータが残っている

対処:

- 追加時に `sites` を確認して重複を止める
- 一覧表示時に `Set` で重複除去する
- 既存データが重複していたら、削除して 1件に戻す

### 7-2. アラートは出るが、後続の処理が止まらない

原因:

- `onAddSite()` の戻り値を確認していない
- `alert` の後に自動選択や閉じる処理が続いている

対処:

- `return false` を返して、成功時のみ次の処理へ進む
- 失敗時は `return;` して止める

### 7-3. DB に重複データが残っている

対処:

- 同名レコードを確認する
- 重複分を削除し、1件だけ残す
- その後に現場を再作成する

## 8. 実務上のルール

この運用を基本ルールにします。

1. まずローカルで動作確認する
2. 画面と数字を人間が確認する
3. 問題がなければ確定する
4. その後に GitHub へ送る
5. コミットメッセージは日本語で残す

---

## 9. 典型的な作業例

### 例: 重複現場名の修正

1. 現場追加時の重複チェックを実装する
2. 一覧で同名が2件出ないか確認する
3. ローカルで `npm run dev` を起動する
4. 現場追加画面で同名入力を試す
5. アラートが出て作成が止まることを確認する
6. 問題なければ「確定です」
7. Claude Code がコミットして GitHub に push する

---

## 10. 最終ルール

修正が完了したら、次の順が最も安全です。

- 見た目確認
- 操作確認
- 数字確認
- 確定指示
- GitHub 送信

> ここを守れば、2か月後に見返したときでも、何をどの順番でやったかが明確になります。
